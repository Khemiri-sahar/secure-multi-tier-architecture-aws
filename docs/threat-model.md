# Threat Model

## Scope & Constraints

This threat model covers a 3 tier web application (a public ALB, a private web/app tier running an Auto Scaling Group of EC2/ECS instances, and an isolated RDS data subnet) plus the security service layer that observes and protects it: KMS, Secrets Manager, GuardDuty, Security Hub, Config, CloudTrail, WAF/Shield, and IAM/SCPs. Consistent with the rest of this repository (see the README's [Scope & Approach](../README.md#scope--approach)), this is a design and documentation exercise. The architecture was designed and documented in detail but was not deployed to a live AWS account, so every threat and control below is evaluated on paper, not against live telemetry. For concreteness, the hypothetical workload is a subscription platform that stores customer account profiles and payment metadata (tokenized card references, not raw PAN) in the RDS data tier. That's the sensitive data this document keeps referring back to.

## Assets

| Asset | Sensitivity | Why it matters |
|---|---|---|
| Data at rest in RDS (customer account and payment metadata) | Critical | This is the worst case outcome the whole architecture is built to prevent, and the reason the data subnet is isolated and has its own dedicated CMK |
| Data at rest in S3 (assets and logs bucket) | Medium | Mixed sensitivity: the static assets are low value on their own, but the same bucket is CloudTrail's delivery target, so its contents include audit relevant metadata |
| Secrets in Secrets Manager (RDS master credential) | Critical | Whoever holds this can bypass the app tier entirely and connect to the database directly with full privileges |
| IAM identities and roles (app tier role, rotation Lambda role, and so on) | High | This is the mechanism every other control depends on. A role with more privilege than it needs is a ready made path for lateral movement |
| Network perimeter (WAF WebACL and ALB boundary) | High | The only point in this architecture directly reachable from the internet. Everything behind it assumes this boundary held |
| CloudTrail logs | Critical | Not just evidence after the fact. If an attacker can tamper with or delete the audit trail, every detective control (GuardDuty, Security Hub, Config) loses its record that anything happened at all. Detection fails silently, which is why log integrity gets treated as seriously as the data it protects |

## Threats

**Compromised web tier credentials pivoting toward the app or data tier.** The web/app tier (the ASG of EC2/ECS instances behind the ALB) is the most exposed compute surface in this architecture, since it's the first thing an attacker reaches after clearing WAF. The real risk isn't that one instance gets popped, it's whether its credentials are also usable against the RDS data tier or the other CMKs. Because the app tier role is scoped narrowly, and each of the four KMS keys gates that role's access with a `kms:ViaService` condition, a stolen app tier credential can be used exactly as far as the app tier is normally allowed to go, and no further into keys or resources it was never granted.

**Data exfiltration attempt against the isolated data subnet.** An attacker who reaches the app tier, or who compromises a principal with query access, could try to pull data out of the isolated data subnet in bulk rather than one record at a time. RDS storage encryption (its own CMK, decrypt gated to the app tier role only) means a stolen snapshot or disk image isn't directly useful, and GuardDuty's account wide detector is positioned to flag anomalous access patterns against it. Neither of those, though, is a control aimed specifically at detecting or blocking bulk data leaving the isolated subnet's network path. That's a narrower gap than what the encryption and detection controls above actually cover.

**Cryptomining or resource hijacking on compute.** A compromised or misconfigured compute tier instance (ASG/EC2/ECS) running attacker code to mine cryptocurrency is the worked example this architecture's incident response path is actually built around. It's the exact GuardDuty finding type, CryptoCurrency, used in the Incident Response Walkthrough. Detection is automatic and account wide through GuardDuty, and response is automatic too, not manual: an EventBridge rule matching severity 7 or higher invokes the incident response Lambda, which quarantines the instance's security group, snapshots it, and tags it, in parallel with an SNS alert. This is the one threat in this document with a fully automated path from end to end, not just detection.

**Reconnaissance activity indicating a compromised IAM principal.** GuardDuty's account wide detector isn't limited to the cryptomining finding type above. Reconnaissance pattern findings (unusual API call patterns, credential use from an unexpected location, enumeration style calls) feed the same detector and the same Security Hub to EventBridge to Lambda pipeline described in the walkthrough. This matters most for the app tier role and the rotation Lambda's role, since those are the two identities with standing access to anything sensitive (the CMKs and the RDS secret, respectively). Reconnaissance against either one is the precursor to the pivot and exfiltration threats above, not a separate incident category on its own.

**Configuration drift, meaning a resource becoming non compliant after initial setup.** A resource that starts out compliant doesn't stay that way automatically. An RDS instance's encryption setting, an EBS volume, the S3 bucket's public access block, or an IAM user's MFA requirement can all be changed out of band after deployment, whether by mistake or by an attacker covering their tracks. Config's four managed rules (`rds-storage-encrypted`, `encrypted-volumes`, `s3-bucket-public-read-prohibited`, `iam-user-mfa-enabled`) catch this continuously rather than at a single point in time, and for this specific threat the response doesn't wait on a human: a non compliant resource triggers an SSM Automation document directly, the parallel loop shown in the incident response diagram alongside the GuardDuty path.

**Over privileged access and insider risk.** The risk here isn't only an external attacker. It's a legitimate principal, whether that's a role or whoever can modify IAM policy, ending up with more access than their tier actually needs, whether through scope creep over time or a single mistake. Two controls apply at two different layers: per tier IAM roles keep each tier's day to day permissions narrow by default, and Service Control Policies act as the backstop above that, denying the disabling of GuardDuty or Config and denying the creation of unencrypted EBS volumes or RDS instances account wide, so that even a role with broad IAM permissions can't quietly turn off the detective controls this document depends on.

**Log tampering or gaps in the audit trail.** If CloudTrail's record can be altered or deleted, or if activity in a region outside the primary trail goes unlogged, every detective control in this architecture (GuardDuty, Security Hub, Config, the incident response Lambda) loses the evidence trail it depends on, without necessarily losing the ability to detect the original event in the first place. That's why this threat gets three separate controls instead of one: a multi region trail so no region is a blind spot, log file validation so tampering is detectable even if it can't be prevented, and delivery to the S3 assets/logs bucket encrypted with its own CMK so the log contents aren't readable by an unauthorized principal even if the bucket were reached.

## Controls

| Threat | Control | Status |
|--------|---------|--------|
| Unauthorized decryption of S3 asset/log objects if a role or key is misused | Dedicated S3 CMK, grant restricted to the app tier role via a `kms:ViaService` condition | Documented, not deployed |
| Unauthorized decryption of RDS database storage | Dedicated RDS CMK, grant restricted to the app tier role via a `kms:ViaService` condition | Documented, not deployed |
| Unauthorized decryption of compute tier EBS volumes | Dedicated EBS CMK, grant restricted to the app tier role via a `kms:ViaService` condition | Documented, not deployed |
| Unauthorized decryption of SSM SecureString config | Dedicated SSM CMK, grant restricted to the app tier role via a `kms:ViaService` condition | Documented, not deployed |
| Stale CMK material increases the value of any single key compromise | Automatic annual key rotation enabled on all four CMKs | Documented, not deployed |
| Long lived RDS master credential increases the compromise window | 30 day automatic rotation via the AWS provided single user RDS rotation Lambda pattern | Documented, not deployed |
| RDS master credential readable by more than the principals that need it | Secrets Manager resource policy denies `GetSecretValue` to everyone except the app tier role and the rotation Lambda's role, and denies access from outside the account | Documented, not deployed |
| Malicious or compromised resource activity, such as cryptomining, going undetected | GuardDuty enabled account wide with S3 Protection, findings routed to Security Hub | Documented, not deployed |
| Security findings and compliance posture scattered across services with no unified view | Security Hub aggregates GuardDuty and Config findings and evaluates the account against CIS AWS Foundations Benchmark and PCI DSS | Documented, not deployed |
| An RDS instance created encrypted today drifts to unencrypted later | Config managed rule `rds-storage-encrypted`, continuous evaluation | Documented, not deployed |
| An EBS volume drifts to unencrypted after creation | Config managed rule `encrypted-volumes`, continuous evaluation | Documented, not deployed |
| The S3 assets/logs bucket becomes publicly readable | Config managed rule `s3-bucket-public-read-prohibited`, continuous evaluation | Documented, not deployed |
| An IAM user is granted console access without MFA | Config managed rule `iam-user-mfa-enabled`, continuous evaluation | Documented, not deployed |
| A non compliant resource stays that way indefinitely without a human noticing | Config auto remediation: a non compliant resource triggers an SSM Automation document directly | Documented, not deployed |
| API activity in a region outside the primary trail goes unlogged | CloudTrail trail enabled in all regions (multi region) | Documented, not deployed |
| CloudTrail log files are tampered with or deleted undetected | CloudTrail log file validation enabled | Documented, not deployed |
| CloudTrail log contents read by an unauthorized principal | CloudTrail logs encrypted at rest using the S3 CMK | Documented, not deployed |
| CloudTrail's own S3 log bucket becomes publicly accessible | S3 bucket policy blocks public access, and Config continuously verifies this | Documented, not deployed |
| L7 attacks (SQLi, generic exploits, credential stuffing or flooding) against the public facing app | WAF WebACL associated directly with the ALB: AWS Managed Core rule group, SQLi rule group, and a custom rate based rule | Documented, not deployed |
| Network or transport layer DDoS against public endpoints | Shield Standard, automatic and always on across all endpoints | Documented, not deployed |
| An over permissioned compute tier role enabling lateral movement | Narrowly scoped, per tier IAM roles, with no shared admin style role spanning tiers | Documented, not deployed |
| A single over permissioned IAM policy silently disabling account wide detective controls | Service Control Policies deny disabling GuardDuty/Config and deny creating unencrypted EBS volumes or RDS instances, account wide | Documented, not deployed |
| A GuardDuty finding sits unactioned while a human triages it, giving an attacker time | EventBridge rule (severity 7 or higher) invokes a Lambda that automatically quarantines the resource's security group, snapshots it, tags it, and publishes an SNS notification | Documented, not deployed |
